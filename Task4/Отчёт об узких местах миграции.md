# Узкие места при миграции

Отчёт к `Диаграмма Исикавы.drawio`.

Переход от файлового ландшафта (Excel, два экземпляра 1С в файловом
режиме, общий диск, Exchange) к распределённой системе при
пятикратном росте данных.

Монолитного приложения, которое надо разрезать, нет — есть набор
разрозненных файловых систем. Поэтому основные риски в данных
и в готовности команды, а не в декомпозиции кода.

## Затрагиваемые компоненты

| Компонент | Было | Станет | Критичность |
|---|---|---|---|
| Журналы приёма, пациентов, платежей | Excel | Операционная БД | Высокая |
| Медкарты | Бумага и сканы | БД с шифрованием | Высокая |
| 1С:Бухгалтерия | Файловый режим | Клиент-серверный, API | Средняя |
| 1С:Торговля | Файловый режим | Без изменений | Низкая |
| ККМ | OLE | Через платёжный шлюз | Средняя |
| Exchange | Транспорт медданных | Только переписка | Высокая |
| Физический сервер | AD, DNS, DHCP, LDAP, файлы, почта | Разделение контуров | Высокая |
| Запись на приём | Телефон | Портал и приложение | Высокая |

## Рекомендации

Приоритет 9:
1) перевести 1С в клиент-серверный режим до начала остальной миграции
2) нанять двух-трёх разработчиков и DevOps либо взять подрядчика
3) разбить миграцию на этапы по процессам, на каждом — параллельная
   работа и возможность отката
4) вынести прикладной контур отдельно, на сервере оставить
   инфраструктурные службы
5) решить вопрос поиска по зашифрованным полям на этапе проектирования:
   детерминированное шифрование либо индекс по хешу фамилии

Приоритет 6:
1) мониторинг и трассировка — до запуска первого сервиса
2) очистка данных — отдельным проектом, не внутри срока миграции
3) событийное взаимодействие для всего, что не требует немедленного ответа
4) Circuit Breaker, Timeout, Retry на внешних вызовах
5) асинхронная запись аудита через очередь
6) сквозной идентификатор пациента и сопоставление записей до миграции

Приоритет 4 и ниже: кеширование справочников, расчёт пулов соединений,
устранение N+1, конвейер сборки, обучение персонала, резервирование
знаний по инфраструктуре, SLA с лабораторией, версионирование
контрактов, назначение офицера ИБ.

## Соразмерность архитектуры команде

IT-отдел из трёх человек без разработчиков получает задачу построить
распределённую систему с платформой приватности, озером данных
и мониторингом.

Предлагаю не строить микросервисы на первом этапе. Модульный монолит
даёт те же границы ответственности и то же разграничение доступа
без операционной сложности. Сервисы выделять позже и по конкретной
причине: разный профиль нагрузки или разный контур безопасности.

Исключение — шлюз интеграции с лабораторией и служба псевдонимизации
с хранилищем соответствий. Их выносим сразу, по требованиям защиты.

## Дорожная карта

| Этап | Срок | Критерий завершения |
|---|---|---|
| 0. Подготовка | 1–2 мес. | 1С в клиент-серверном режиме, метрики собираются, команда есть |
| 1. Данные | 2–3 мес. | Данные в БД, дубли разобраны, поиск по фамилии работает |
| 2. Запись на приём | 2 мес. | Больше половины записей через портал |
| 3. Медкарты | 3 мес. | Карты в системе, обращения фиксируются |
| 4. Интеграции | 2 мес. | Почта как канал медданных закрыта |
| 5. Аналитика | 2 мес. | Отчёты на обезличенных данных, теневые копии удалены |

Итого 12–14 месяцев. Переход на следующий этап — после месяца работы
предыдущего без отката.
