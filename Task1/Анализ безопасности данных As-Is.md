# Анализ безопасности данных (As-Is)

Диаграммы: `DFD_as-is.drawio`, `DFD_to-be.drawio` — по листу на процесс.
Процессы: запись на приём, медкарта, анализы, оплата, отчётность.
Учёт ТМЦ исключён — ПДн пациентов там нет.

## Конфиденциальные данные вне учёта

Вне IT-систем:
1) бумажные согласия и ИДС — реестра нет
2) бумажные медкарты — доступ не журналируется
3) анкеты с хроническими заболеваниями
4) распечатка списка приёма на стойке

В системах, но не классифицированы:
1) журнал записи в Excel — связка «ФИО + специалист» это врачебная тайна
2) календарь Outlook — ФИО пациента в теме встречи
3) почтовые ящики — вложения, «Отправленные», локальные OST
4) чеки ККМ и данные ОФД — наименование услуги раскрывает профиль обращения
5) станция бизнес-аналитика — теневые копии выгрузок с ПДн
6) очередь печати, корзина, теневые копии тома
7) резервные копии — нигде не упомянуты
8) данные соискателей — процесс не описан

Проверить: ведёт ли ресепшен переписку с пациентами в мессенджерах.

## Аудит мер безопасности

Критический разрыв:
1) разграничение доступа — только доменная аутентификация
2) аудит доступа — отсутствует
3) шифрование at rest — Excel, сканы, 1С открытым текстом
4) шифрование in transit — SMB, OLE, обычная почта

Не реализовано: Privacy by Design и by Default, минимизация данных,
Data Lineage, обезличивание для аналитики, классификация и тегирование,
управление согласиями, жизненный цикл данных, DLP, реагирование
на инциденты. Резервное копирование не описано.

## Данные для защиты

K1 обезличенные, K2 ПДн общего характера, K3 документы и финансы,
K4 спецкатегории и врачебная тайна.

| Данные | Класс | Шифрование | Маскирование | Обезличивание |
|---|---|---|---|---|
| Справочники, расписание без ФИО | K1 | — | — | — |
| ФИО | K2 | AES-256 на поле | «Иванов И. И.» | Суррогатный id |
| Телефон, почта | K2 | AES-256 на поле | `+7 (9XX) XXX-12-34` | Удаление |
| Дата рождения | K2 | AES-256 на поле | — | Возрастная группа |
| Адрес, место работы | K2 | AES-256 на поле | До города | Регион |
| Факт обращения | K4 | AES-256 на поле | В расписании только id записи | Разрыв связи со специалистом |
| Паспорт, полис, СНИЛС | K3 | AES-256, отдельный ключ | Частичное сокрытие | Удаление |
| Реквизиты карты | K3 | Не хранятся | Последние 4 цифры | Удаление |
| Хронические заболевания | K4 | AES-256, отдельный ключ | Лечащий врач | Категория МКБ-10 |

## Тегирование

Тег на атрибуте в модели данных, наследуется витринами, выгрузками,
API и логами.

```yaml
classification:
  level: K4
  categories: [health, med_secret]
  owner: "Медицинская служба"
  legal_basis: "152-ФЗ ст.10 ч.2 п.4"
  retention: "25y"
  erasure: restrict          # delete | restrict | anonymize
  encryption: field-aes256
  masking: role-based
  export_allowed: false
  analytics: anonymize-required
```

`erasure` отделяет удаляемое от того, что хранится 25 лет по закону.

Инструменты: OpenMetadata или DataHub, аннотации полей в коде,
метки на колонках СУБД, метатеги dbt, OpenLineage, Apache Ranger.

Автоконтроль:
1) поле без тега при миграции схемы — сборка не проходит
2) K3/K4 в логе или ответе API без маскирования — сборка не проходит
3) витрина из K4 без обезличивания — сборка не проходит
4) остаточные ПДн в обезличенном слое — алерт, витрина недоверенная
5) обращение к K4 вне лечащей связи — алерт офицеру ИБ

Порядок: K4 → K3 → K2 → остальное. Без тега к концу миграции — K2.
